# Diagrams: Archify, not Mermaid

**Never write a ```mermaid code fence in a PRD, even out of habit or because it feels faster.** A real audit of this tool's own saved PRDs found the drafting model reaching for Mermaid on its own even after being told not to (Mermaid is by far the most familiar way to draw a flowchart; Archify's typed-JSON approach is new) -- and every one of those slips reached the Google Doc as raw, unreadable diagram source text instead of an image, because the automatic Doc export has no way to render Mermaid at all. The app now actively rejects any `save_prd_markdown` or `create_google_doc` call whose content still contains a ```mermaid fence, so a slip costs an extra round trip rather than silently shipping -- but writing it correctly the first time is always better than being bounced back.

Every flowchart and sequence diagram in a PRD is built with **Archify** (via the `render_archify_diagram` tool), not hand-written Mermaid syntax. Archify takes a typed JSON document ("IR"), validates it, and renders a real diagram image server-side -- there is no plain-text diagram syntax to write directly into the PRD anymore.

## The workflow

1. **Decide the type.** `workflow` for a flow with branches/decision points (this replaces Mermaid `flowchart`). `sequence` for a multi-actor call sequence over time (this replaces Mermaid `sequenceDiagram`). Don't reach for `architecture`, `dataflow`, or `lifecycle` unless the content genuinely fits their specific shape (a components-and-boundaries system diagram, a data-lineage/PII-boundary diagram, or a states-and-transitions diagram, respectively) -- most PRD flows are `workflow` or `sequence`.
2. **Author the IR** per the shapes below.
3. **Call `render_archify_diagram`** with `{ type, title, ir }`.
   - **Success** returns an exact fenced block, e.g. `` ```archify\n{"id":"...","title":"..."}\n``` ``. Paste that block verbatim into the PRD content at this point -- it's a pointer the app resolves into the real rendered image later, not something to edit or reformat.
   - **Failure** returns Archify's own diagnostics: `{code, message, subject, evidence, supportedFixes}` per problem, generated by real schema/layout validation, not a guess. Fix the IR based on what the diagnostic actually says (a dangling edge reference, an unknown node id, a schema violation) and call the tool again. Never retry blindly without reading what changed.
4. **Never fabricate the fence yourself.** Only ever paste the exact block the tool returned from a successful call -- a hand-typed `` ```archify `` block with a made-up id will render as a broken image with nothing to show for it.

## Universal rules for every diagram

- **Omit `meta.animation`, or set it to `"none"`.** These diagrams are captured as a single static screenshot the moment the page loads -- `"trace"` animation risks the screenshot landing mid-draw, showing an incomplete diagram. Static is also simply what a PRD needs; the interactive/animated viewer experience isn't part of what gets embedded.
- **Keep node/participant counts sane.** 6-12 nodes for a workflow, 4-8 participants for a sequence is the sweet spot matching what fits legibly in a document -- same judgment call Mermaid needed ("keep node labels short," from `tone-and-conventions.md`). A flow that's genuinely bigger than that is a sign to split it into two diagrams (e.g. by sub-flow), not to cram more into one.
- **Every id must actually exist.** `additionalProperties: false` is set at every level of Archify's schema, and every edge/message endpoint must reference a real node/participant id declared elsewhere in the same document -- a typo'd id is the single most common validation failure; `render_archify_diagram`'s diagnostic will name the exact unknown id if this happens.
- **Titles and labels stay in business-logic language**, per `tone-and-conventions.md`'s "Business logic first, APIs as supporting reference" -- a node/participant label is what a non-engineer would call that step or actor, not a class/method name.

## `workflow` -- branching flows

Required top level: `schema_version` (use `2`), `diagram_type: "workflow"`, `meta.title`, `lanes`, `phases`, `groups`, `mainPath`, `nodes`, `edges`.

Layout is grid-based, not pixel-based -- this is the easy one:
- **`lanes`**: one row per actor/system, e.g. `{"id": "ui", "label": "Boss App"}`. Order matters (top to bottom).
- **`nodes`**: each one declares `lane` (which row) and `col` (which column, an integer starting at 0) -- that's the entire layout. `type` picks the node's visual kind: `frontend`, `backend`, `database`, `cloud`, `security`, `messagebus`, or `external`.
- **Always set an explicit `width` on every node, wide enough for its label.** The default node width (92px) is too narrow for almost any real label -- omitting `width` reliably fails validation with `layout/constraint: Label "..." is wider than node "..." (92px)`. Use `width: Math.max(92, label.length * 9 + 40)` as a mechanical rule (roughly 9px per character plus padding) rather than guessing per node.
- **`edges`**: `{id, from, to}` referencing node ids, optional `label`.
- **`phases`** and **`groups`** are optional visual groupings (a dashed box around a column range, or a lane+column range) -- fine to leave `phases: []` and `groups: []` for a simple flow; add them only when a distinct stage or exception path genuinely benefits from being visually boxed.
- **`mainPath`**: the ordered list of node ids for the primary/happy-path route, used to highlight it -- include every node on the main flow in order; branch-only nodes (a failure/retry path) don't belong in it.

Minimal worked example:

```json
{
  "schema_version": 2,
  "diagram_type": "workflow",
  "meta": { "title": "Gold Activation" },
  "lanes": [
    { "id": "app", "label": "Boss App" },
    { "id": "backend", "label": "toll-gold" }
  ],
  "phases": [],
  "groups": [],
  "mainPath": ["offer", "select", "activate", "confirm"],
  "nodes": [
    { "id": "offer", "lane": "app", "col": 0, "type": "frontend", "label": "Gold offer shown" },
    { "id": "select", "lane": "app", "col": 1, "type": "frontend", "label": "Customer selects plan" },
    { "id": "activate", "lane": "backend", "col": 2, "type": "backend", "label": "Subscription activated" },
    { "id": "confirm", "lane": "app", "col": 3, "type": "frontend", "label": "Confirmation shown" },
    { "id": "denied", "lane": "backend", "col": 2, "type": "security", "label": "Activation rejected" }
  ],
  "edges": [
    { "id": "e1", "from": "offer", "to": "select" },
    { "id": "e2", "from": "select", "to": "activate" },
    { "id": "e3", "from": "activate", "to": "confirm", "variant": "emphasis" },
    { "id": "e4", "from": "activate", "to": "denied", "label": "eligibility check fails", "variant": "security", "role": "error" }
  ]
}
```

## `sequence` -- multi-actor call sequences

Required top level: `schema_version` (use `1`), `diagram_type: "sequence"`, `meta.title`, `participants`, `messages`. `segments` and `activations` are optional but worth including (they're what makes the diagram readable).

This one uses **pixel Y-coordinates** for message order, not a grid -- don't try to eyeball spacing. Use this mechanical rule instead:
- Assign each message, in call order, `y = 150 + 40 * index` (index starting at 0). This guarantees strictly increasing, evenly-spaced values with no overlap, regardless of how many messages there are.
- For each `activations` entry (the vertical bar showing a participant is "doing work"), set `from` to the `y` of the message that starts its involvement and `to` to the `y` of the message that ends it, each nudged in by about 10px (`from + 10`, `to - 10`) so the bar doesn't visually collide with the message arrows at its own edges.
- `segments` (optional labeled phase bands, e.g. "Request" / "Fallback" / "Response") should span a `from`/`to` range covering the `y` values of the messages in that phase, with about 15px of padding on each side.

Minimal worked example:

```json
{
  "schema_version": 1,
  "diagram_type": "sequence",
  "meta": { "title": "Auto-Recharge Mandate Check" },
  "participants": [
    { "id": "app", "type": "frontend", "label": "Boss App" },
    { "id": "tzf", "type": "backend", "label": "tzf-fastag" },
    { "id": "bank", "type": "external", "label": "Bank" }
  ],
  "messages": [
    { "id": "m1", "from": "app", "to": "tzf", "y": 150, "label": "check auto-recharge eligibility", "variant": "default" },
    { "id": "m2", "from": "tzf", "to": "bank", "y": 190, "label": "verify mandate", "variant": "emphasis" },
    { "id": "m3", "from": "bank", "to": "tzf", "y": 230, "label": "mandate active", "variant": "return" },
    { "id": "m4", "from": "tzf", "to": "app", "y": 270, "label": "eligible", "variant": "return" }
  ],
  "activations": [
    { "participant": "tzf", "from": 160, "to": 260, "type": "backend" },
    { "participant": "bank", "from": 200, "to": 220, "type": "external" }
  ]
}
```

`column_fit: "spread"` in `meta` (instead of the default `fixed`) is worth setting whenever participant labels are long -- it derives column spacing from the diagram's own width instead of a fixed gap, which otherwise cramps long labels.

## When something isn't covered above

This file covers the fields needed for the vast majority of PRD flows. For anything else (legends, brand marks, locale, guided views, an `architecture`/`dataflow`/`lifecycle` diagram), the fastest path is to author your best guess and call `render_archify_diagram` -- its schema validation returns a precise, path-prefixed diagnostic naming exactly which field is wrong or missing, which is faster and more reliable than trying to derive the full schema from first principles. `vendor/archify/schemas/` is not reachable from this app's `read_repo_file`/`search_repo` tools (those are scoped to Blackbuck's product repos only) -- the validate-and-repair loop is the intended way to close any gap this guide doesn't cover.
